# AI 영상 편집 요청 앱 최종 기획

> **현재 단계 변경 · 2026-10-14:** 사용자의 최신 결정에 따라 첫 프로토타입은 「시간별 장면 내용–피드백 전달」에 집중한다. 기본 화면·전달물·검수 기준은 [피드백프로토타입](피드백프로토타입.md)을 우선 적용한다. 아래 자동 편집 제품 기획은 이후 확장 방향으로 보존하며 해석·승인·렌더는 기본 전달 흐름의 선행 조건으로 두지 않는다.

2026년 10월 14일 · 데스크톱 우선 · 1인용 제작 도구 · 대상 저장소 [Muuuuoouuun/video_-interference](https://github.com/Muuuuoouuun/video_-interference)

**영상을 보면서 구간을 잡고 글이나 그림으로 수정 요청을 남기면, AI가 편집 명령으로 번역한다. 사용자는 그 해석을 승인하고 실제 수정 영상을 비교한다.** 첫 제품은 로컬에서 실행하는 웹앱으로 만든다. React 화면과 Node 워커를 나누고, FFmpeg로 실제 MP4를 출력한다.

작업 폴더는 `/Volumes/OneTouch/video_interference`로 정한다. 데스크톱 사용 흐름을 우선 완성하고 모바일은 후속 개발 범위로 둔다.

첫 사용자는 혼자 영상을 제작하는 사용자다. 기존 영상의 컷, 속도, 자막, 간단한 그래픽을 반복 수정하는 작업을 중심으로 잡는다. 공유 링크, 팀 권한, 외부 리뷰어 관리보다 **요청부터 결과까지 한 바퀴가 정확히 도는 것**이 우선이다.

## 확정한 제품 원칙

제품 판단의 우선순위는 **1. 본질 → 2. 편의성 → 3. 사용성**이다. 장면과 수정 의도가 실제 결과까지 정확히 이어지는 것을 먼저 지키고, 반복 입력을 줄이며, 현재 상태와 다음 행동을 분명히 한다. 구체적인 개발·검수 기준은 [제품원칙](제품원칙.md)에 정리한다. 요청은 먼저 저장하고 나중에 해석해도 된다.

1. **요청과 실행 명령을 분리한다.** 사용자의 원문은 보존하고, AI가 제안한 `EditOp`는 따로 수정하고 승인한다.
2. **승인한 명령만 렌더한다.** 요청 입력, AI 해석, 실행 승인, 결과 채택을 별도 동작으로 둔다. 승인은 카드 안에서 하므로 매번 확인 팝업을 띄우지 않는다.
3. **원본과 버전 기록을 보존한다.** 새 버전은 원본과 편집 스냅샷으로 렌더한다. 이전 압축 결과를 반복 재편집하는 데 따른 세대 손실을 줄인다. H.264로 다시 인코딩하는 결과 자체를 무손실이라고 표현하지 않는다.
4. **메모는 실행하지 않는다.** 댓글, 드로잉, 음성, 참고 이미지는 기본적으로 지시 자료다. 영상에 포함할 에셋은 역할을 명시한다.
5. **요청은 숫자 시각보다 장면을 따라간다.** 작성 버전과 원본 앵커를 함께 저장해 컷과 배속 뒤에도 같은 장면을 찾는다.
6. **지원 범위 밖의 요청은 보류한다.** 움직이는 얼굴 추적이나 장면 재생성을 단순한 박스·컷 작업으로 조용히 대체하지 않는다.

## 첫 사용 사례와 범위

처음에는 이미 편집된 쇼츠, 광고, 설명 영상의 수정에 집중한다. **30초에서 10분 사이 SDR 영상, 원본 영상 한 개, H.264와 AAC를 담은 MP4 출력**을 개발·검증의 기본 범위로 잡는다. 이 길이는 성능 보장이 아니라 샘플 범위다. 여러 카메라 동기화와 전문 색보정은 후속으로 둔다.

| 작업 상황 | 입력 예시 | 검수할 결과 |
|---|---|---|
| 불필요한 장면 제거 | I/O 지정 후 “여기 삭제해줘” | 구간이 제거되고 앞뒤 영상·음성이 연결됨 |
| 영상 앞뒤 정리 | 구간 지정 후 “이 부분만 남겨줘” | 선택 구간만 있는 새 버전 |
| 템포 조절 | “이 구간 2배속” | 영상·음성이 같은 길이로 줄어듦 |
| 자막 추가 | “여기 3초 동안 ‘지금 시작하세요’” | 독립 자막 레이어가 지정 구간에 표시됨 |
| 그래픽 위치 지정 | 박스를 그린 뒤 “여기에 제목” | 박스 위치에 제목이 표시됨 |
| 이미지 삽입 | PNG 첨부 후 “오른쪽 위에 넣어줘” | 삽입 에셋이 지정 구간에 표시됨 |
| 스타일 참고 | 이미지 첨부 후 “이 색과 배치를 참고해줘” | 지원하는 스타일 속성의 제안 |
| 음성 지시 | 선택 구간에서 녹음 | 전사 확인 후 동일한 EditOp 흐름으로 연결 |

첫 실행 엔진의 필수 기능은 `cut`, `trim`, `speed` 세 개다. 이번 초안에서는 자막·정적 이미지·음량도 같은 구조로 구현을 진행한다. 지원 목록은 실제 렌더로 검증된 기능을 기준으로 표시한다.

| 차용할 방식 | 우리 앱에서의 적용 |
|---|---|

| 펜·박스·화살표 | 위치 설명과 편집 대상 영역 지정 |
| 첨부파일 | 참고 이미지와 삽입 에셋 역할 선택 |
| 댓글 스레드 | AI 질문, 사용자의 보완 답변, 재해석 |
| 버전 스택 | 편집 스냅샷과 렌더 결과를 함께 보관 |
| 나란히 비교 | 대응 장면 또는 요청 전후 구간 비교 |

Frame.io도 전사와 자막 기능을 제공한다. 이 제품의 차별점은 “AI가 있느냐”보다 **내가 남긴 요청을 검증 가능한 편집 명령과 실제 출력으로 연결하는 과정**이다. [Frame.io 전사와 자막](https://help.frame.io/en/articles/10966531-frame-io-transcription-overview).

## 메인 화면

작업 화면 하나에서 영상, 시간축, 요청, 실행 결과를 함께 다룬다. 빈 화면의 첫 행동은 **영상 열기**다. 프로젝트 목록과 에셋 목록은 왼쪽에 작게 두고, 자주 쓰는 기능은 플레이어와 요청 패널에 집중한다.

```text
┌ 프로젝트 이름 · 현재 버전 ─────────── 비교 ─ MP4 내보내기 ┐
│ 원본·에셋     │ 영상 플레이어                  │ 요청·메모   │
│ 버전 기록     │ 박스 / 화살표 / 펜             │ 시간·범위   │
│               │                                │ 원문·첨부   │
│               │ 재생 / 보기 배속 / 프레임 이동 │ 해석 카드   │
│               ├────────────────────────────────┤ 승인·수정   │
│               │ 시간축 · I/O · 요청 마커       │ 요청 작성   │
│               │ 선택 구간 00:12 → 00:18        │ 승인 2개    │
└───────────────┴────────────────────────────────┴ 새 버전 만들기┘
```

| 영역 | 핵심 행동 | 바로 보여줄 정보 |
|---|---|---|
| 프로젝트·버전 | 파일 열기, 버전 선택, 되돌리기 | 원본, 부모 버전, 채택 버전 |
| 플레이어 | 재생, 시킹, 보기 배속, 정지 프레임 표시 | 현재 시각, 영상 크기, 선택된 요청 |
| 드로잉 | 박스·펜·화살표, 지우기 | 해당 프레임의 지시용 표시 |
| 시간축 | I/O, 요청 마커 클릭, 선택 구간 반복 | 구간 길이와 요청 위치 |
| 요청 패널 | 텍스트·음성·첨부 입력, AI 해석 | 원문과 해석 차이, 필요한 질문 |
| 해석 카드 | 파라미터 수정, 승인, 제외 | 작업 종류, 대상 범위, 예상 길이 |
| 실행·비교 | 승인한 명령 렌더, 결과 채택 | 진행 상태, 실패 원인, 새 버전 |

단축키는 Space 재생·정지, I/O 구간 지정, 좌우 이동, Escape 선택 해제부터 지원한다. 텍스트 입력과 대화상자가 활성화된 동안 플레이어 단축키를 막는다. 프레임 인덱스가 준비되지 않은 초안에서는 좌우 이동을 “프레임 정확”이라고 표시하지 않는다.

### 요청 카드에서 승인하는 방법

요청 아래에 “12.0–18.0초 · 2배속 · 음성 높이 유지 · 6초 → 3초”처럼 AI가 이해한 결과를 표시한다. 한 요청이 `speed`와 `subtitle`로 나뉘면 두 개의 작업을 따로 보여주고 각각 승인할 수 있다.

카드에서 해석을 고치면 승인은 해제된다. 상단 실행 버튼은 “승인한 2개로 새 버전 만들기”처럼 대상 수를 표시한다. 승인되지 않은 작업, 사람용 메모, 보완 질문은 실행 목록에 들어가지 않는다. 렌더 완료 후에는 “새 버전 보기”와 “이 버전 채택”을 제공한다.

## 입력 역할과 상태

댓글을 입력하는 것과 편집을 요청하는 것을 구분한다. 작성창에서 **편집 요청 / 메모**를 선택한다. 요청에는 텍스트 외의 자료를 붙일 수 있고, 메모도 시간축에 남지만 렌더 대상이 되지 않는다.

| 자료 | 기본 역할 | 출력에 넣는 조건 |
|---|---|---|
| I/O | 요청 대상 범위 | 삭제·유지·배속 등 작업 지정 |
| 드로잉 | 위치·의도 설명 | 도형 레이어 생성 작업을 승인 |
| 보기 배속 | 플레이어 재생 설정 | `speed` 작업으로 별도 승인 |
| 참고 이미지 | 스타일·배치 설명 | `insert` 역할과 overlay 작업 지정 |
| 음성 댓글 | 편집 지시 | 본편 음성 에셋으로 별도 등록 |
| 전사 문구 | 지시의 텍스트 표현 | subtitle 작업의 문구로 별도 확정 |

음성 녹음을 시작할 때 프레임·구간을 고정한다. 녹음 중 플레이헤드가 움직여도 대상은 바뀌지 않는다. 전사 결과는 사용자가 수정할 수 있다. 자동 받아쓰기는 음성 댓글의 전사와 본편 전체 자막 생성을 별도 기능으로 다룬다.

요청 상태와 렌더 상태를 섞지 않는다.

| 객체 | 상태 |
|---|---|
| Request | `draft → submitted → interpreting → proposed`, 분기 `needs_clarification / unsupported / failed` |
| EditOp | `proposed → approved / rejected`, 수정하면 다시 `proposed` |
| RenderJob | `queued → running → succeeded / failed / canceled` |
| Version | `rendering → ready`, 사용자가 프로젝트의 `activeVersionId`를 선택 |
| 적용 기록 | 승인한 EditOp가 어떤 Version에 반영되었는지 별도 기록 |

부분 승인과 복수 버전 적용을 표현하기 위해 요청 전체를 단순히 `applied`로 덮어쓰지 않는다. 완료한 요청 카드에는 반영된 버전과 작업별 결과를 보여준다.

## 실행 명령과 AI 역할

AI는 지원 목록 안에서 구조화된 `EditOp`를 제안한다. 사용자의 의도를 해석하는 단계와 미디어를 처리하는 단계를 분리한다. 같은 명령 스키마를 수동 버튼, 자연어 해석기, 렌더러가 공유한다.

| EditOp | 필수 값 | 구현 순서와 범위 |
|---|---|---|
| `cut` | 대상 구간 | 첫 실행 · 구간 삭제 |
| `trim` | 남길 구간 | 첫 실행 · 하나의 연속 구간 |
| `speed` | 구간, 배율, 음성 정책 | 첫 실행 · 일정 배속 |
| `subtitle` | 구간, 문구, 스타일 | MVP 확장 · 독립 자막 레이어 |
| `overlay` | 구간, 텍스트·이미지·도형, 위치 | MVP 확장 · 정적 요소 |
| `audio` | 구간, 음량 | MVP 확장 · 원본 음량·음소거 |
| `zoom` | 구간, 영역 | 후속 · 고정 크롭, 트래킹은 별도 |

사람용 `note`는 저장되는 댓글 종류이며, 실행 가능한 EditOp 목록에 넣지 않는다. 자막 수정은 앱에서 만든 레이어나 가져온 자막을 대상으로 한다. 이미 영상 픽셀에 구워진 자막 교체에는 덮어쓰기·복원 처리가 필요하므로 별도 작업이다.

컷·배속은 FFmpeg 필터그래프로 컴파일한다. `trim/atrim`, `setpts/asetpts`, `atempo`를 사용하고, 자막·정적 그래픽도 지원되는 필터나 이미지 합성으로 확장한다. 필터 지원 여부와 폰트는 설치된 FFmpeg 빌드에서 확인한다. [FFmpeg 필터 문서](https://ffmpeg.org/ffmpeg-filters.html).

### 해석에 제공할 맥락

요청 원문, 기준 버전, 선택 범위, 시작·중간·끝 프레임, 드로잉, 첨부 역할, 기존 레이어, 지원 작업 목록을 묶어서 전달한다. 전사 기능이 있으면 해당 구간의 문구도 제공한다. 선택 범위 밖의 맥락이 필요할 때만 앞뒤 프레임을 추가한다.

AI의 응답은 `operations`, `questions`, `unsupportedReasons`로 나눈다. 스키마 검증, 구간 존재 여부, 에셋 역할, 허용 파라미터, 명령 간 충돌을 워커에서 검사한다. 잘못된 범위와 빠진 문구는 질문으로 돌려보낸다.

모델이 생성한 `confidence`는 참고값이다. `0.6` 같은 숫자를 실행 안전성 기준으로 삼지 않는다. **필수값 충족, 지원 기능 여부, 충돌 없음, 사용자의 승인**이 실행 조건이다. 모델이 생성한 셸 명령이나 임의 코드는 실행하지 않는다.

AI 공급자는 어댑터로 연결한다. Claude 등 멀티모달 API를 교체할 수 있게 하고, Agent SDK는 필수 의존성으로 두지 않는다. 초안에서 정해진 한국어 패턴을 파싱하는 모드를 제공하면 UI에 **로컬 규칙 해석**이라고 표시한다. 실제 비전 모델이 연결되지 않은 모드를 AI 이미지 이해 기능으로 소개하지 않는다.

## 시간과 화면 위치 설계

이 제품의 핵심 데이터는 요청의 앵커다. 영상이 짧아졌다고 사용자가 지정한 장면이 바뀌면 안 된다.

| 값 | 보존할 의미 |
|---|---|
| `baseVersionId` | 사용자가 보고 요청한 버전 |
| `viewRange` | 당시 플레이어에서 선택한 구간 |
| `sourceAssetId` | 원본 파일 |
| `sourcePts`와 `timeBase` | 원본 프레임의 실제 재생 시각 |
| `clipInstanceId` | 같은 원본이 반복될 때 어느 배치인지 |
| `lineageId` | 분할된 클립과 원래 클립의 관계 |
| `layerId` | 수정 대상인 자막·그래픽 레이어 |

범위는 시작을 포함하고 끝을 제외하는 `[in, out)`으로 통일한다. 내부 정밀 계산은 정수 PTS와 유리수 비율을 사용하고, 화면에서 초와 타임코드로 표현한다. JSON에서 큰 정수는 문자열로 직렬화한다.

**프레임 번호만 저장하는 설계는 채택하지 않는다.** 29.97fps 같은 고정 프레임레이트는 분수 fps로 계산할 수 있지만, VFR 원본은 프레임마다 간격이 다를 수 있다. ffprobe로 원본 PTS 인덱스를 준비하고 프록시와 원본의 매핑을 관리한다.

브라우저의 `requestVideoFrameCallback`은 표시된 프레임의 `mediaTime`을 관찰하는 데 사용한다. 콜백 자체가 프레임 정확한 탐색을 보장하지는 않는다. 정밀 선택은 원본 프레임 인덱스와 연결해야 한다. [MDN 프레임 콜백 문서](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback).

### 편집 뒤의 앵커 규칙

60초 영상의 12–18초를 2배속으로 바꾸면 새 길이는 57초다. 원본 24초 장면은 결과 21초로 이동한다. 그 장면에 남긴 요청도 21초 위치로 대응시킨다.

삭제된 장면에 붙은 요청은 “대상 구간 삭제됨”으로 남긴다. 가까운 다른 장면에 자동으로 붙이지 않는다. 여러 출력 구간으로 나뉜 범위는 앵커 세그먼트를 여러 개로 저장한다. 같은 원본을 두 번 배치하면 클립 인스턴스를 구분한다.

드로잉은 검은 여백을 제외한 실제 영상 영역의 0–1 좌표로 저장한다. 회전·크롭·화면 비율을 반영하는 변환을 함께 기록한다. 고정 박스와 움직이는 대상 추적을 별도 기능으로 둔다.

### 레이어와 충돌 규칙

- 자막·그래픽의 기본 노출은 대상 장면을 따른다. 일부가 삭제되면 살아 있는 구간에만 표시하고 배속이면 길이도 같은 비율로 변한다.
- “3초 동안 표시”를 명시하면 시작은 장면 앵커, 길이는 출력 시간 기준이다. 이 정책을 해석 카드에 표시한다.
- 완전히 삭제된 구간의 새 그래픽은 자동 적용하지 않고 충돌로 보류한다.
- 같은 범위의 서로 다른 배속은 곱해서 실행하지 않는다. 하나를 선택하거나 범위를 나눠야 한다.
- 같은 기준 버전에서 작성된 요청은 앵커를 먼저 해결한 뒤 컷·배속·레이어를 한 번에 컴파일한다.

미리보기와 최종 출력은 같은 시간축 계산 결과를 사용한다. 미리보기의 해상도·비트레이트만 다르게 한다. 비교 화면은 동일한 초를 강제로 동기화하기보다 원본 앵커로 대응 장면을 찾는다.

## 데이터 모델과 버전

| 엔티티 | 주요 내용 |
|---|---|
| Project | 이름, 에셋, 채택 버전, 출력 설정 |
| Asset | 원본·프록시·이미지·음성 경로, 해시, 미디어 정보 |
| Version | 부모 버전, 편집 스냅샷, 출력 경로, 생성 원인 |
| ClipInstance | 원본 범위, 속도, 배치, 분할 계보 |
| Comment | 사용자·AI의 원문, 종류, 스레드 관계 |
| Request | 댓글 참조, 대상 앵커, 입력 revision, 해석 상태 |
| Annotation | 벡터 도형, 좌표 변환, 작성 프레임 |
| Attachment | 에셋 참조, `reference / insert / instruction` 역할 |
| EditPlan | 기준 버전, 제안 명령, 질문, 검증 결과, 해시 |
| RenderJob | 승인 스냅샷, 진행 상태, 로그, 결과 버전 |

이 모델은 제품 기준이다. 초안에서는 Comment와 Request를 같은 저장 레코드 안에서 관리할 수 있으나, 사용자 원문과 생성된 명령은 분리된 필드로 둔다.

```ts
type Anchor = {
  baseVersionId: string;
  viewRange: { inUs: number; outUs: number };
  segments: Array<{
    sourceAssetId: string;
    clipInstanceId: string;
    ptsIn: string;
    ptsOut: string;
    timeBase: { num: number; den: number };
  }>;
};

type EditOp = {
  id: string;
  requestId: string;
  requestRevision: number;
  anchor: Anchor;
  type: 'cut' | 'trim' | 'speed' | 'subtitle' | 'overlay' | 'audio' | 'zoom';
  params: Record<string, unknown>; // 실제 구현은 작업별 판별 가능한 스키마
  status: 'proposed' | 'approved' | 'rejected';
};
```

실제 구현에서는 `params`를 작업별 판별 가능한 스키마로 제한한다. 위 코드는 앵커와 요청 revision의 관계를 보여주는 축약형이다.

렌더를 시작할 때 `baseVersionId`, `planHash`, `requestRevision`, 승인한 명령 목록을 고정한다. 실행 중에 요청을 수정해도 해당 작업의 입력은 변하지 않는다. 새 수정은 다음 계획으로 간다. 다른 버전을 채택한 후 이전 계획을 실행하려면 원래 버전의 분기로 만들거나 새 기준에 재해석한다.

새 버전은 편집 상태 JSON과 렌더 결과를 함께 가진다. 원본 `v1`로 돌아가는 동작은 원본을 다시 인코딩할 필요가 없다. `v3`는 `v2.mp4`가 아니라 원본과 v3 편집 스냅샷으로 렌더한다.

## 기술 구성

| 계층 | 첫 선택 | 선택 이유 |
|---|---|---|
| UI | React, TypeScript, Vite | 로컬 작업 화면을 빠르게 실행·검증 |
| API·워커 | Node.js, TypeScript | 파일 가져오기, AI 연결, 렌더 작업을 UI와 분리 |
| 미디어 | native FFmpeg와 ffprobe | 원본 검사, 컷·배속, MP4 출력 |
| 정적 그래픽 | SVG와 sharp | 텍스트·도형을 PNG로 만들어 FFmpeg 합성 |
| 표시·드로잉 | HTML video, SVG | 영상 영역의 벡터 좌표 저장 |
| 저장 | SQLite와 스키마 버전이 있는 JSON | 로컬 요청·작업 복구, 편집 스냅샷 보존 |
| AI·전사 | 교체 가능한 공급자 어댑터 | 모델·가격·로컬 전사 선택을 분리 |
| 모션 그래픽 | 후속 Remotion 어댑터 | 정적 합성으로 부족한 템플릿부터 추가 |
| 데스크톱 | 사용성 검증 후 Tauri 후보 | OS 파일 선택·원본 직접 참조·바이너리 패키징 |

첨부안의 Next.js도 가능한 선택이지만 SSR과 웹 계정이 없는 첫 로컬 버전에서는 필수 이점이 적다. Vite UI와 독립 워커로 시작한다. 클라우드 버전에는 파일 저장·업로드·계정·권한·작업 큐를 추가해야 하므로 같은 코드를 올리는 것만으로 완성되지는 않는다.

Node에 포함된 `node:sqlite`를 사용할 수 있다. 실행 런타임을 고정하고 지원하는 API만 사용한다. ORM은 필요해질 때 추가한다. [Node SQLite 문서](https://nodejs.org/api/sqlite.html).

브라우저의 File 객체에서 원본 절대 경로를 얻었다고 가정하지 않는다. 첫 로컬 웹앱은 파일을 localhost 워커에 스트리밍해 프로젝트 저장소로 가져온다. 데스크톱 버전에서는 OS 파일 선택으로 직접 참조해 큰 파일의 복사를 줄인다.

워커는 localhost에서 실행하고, 미디어는 asset ID로 접근한다. API 키는 워커 설정에 보관한다. FFmpeg는 고정 실행 파일에 검증된 인수 배열로 호출한다. 한 번에 렌더 한 개부터 처리하고 취소·재시작 복구를 확장한다. 클라우드 AI를 연결한 모드는 선택 프레임과 요청 자료를 외부 API에 전송하므로 완전한 오프라인 모드와 구분한다.

### 저장소 구성

```text
video_-interference/
  apps/web/                플레이어, 시간축, 요청·승인·버전 UI
  apps/worker/             localhost API, ingest, AI, 작업 큐, FFmpeg
  packages/core/           요청·EditOp·앵커·버전 공통 스키마
  packages/edit-engine/    구간 계산, 충돌 검사, 시간축 컴파일
  docs/                    기획과 기술 결정
  fixtures/                작은 CFR·VFR·무음·회전 테스트 영상
  storage/                 원본, 첨부, 프록시, 버전, SQLite · Git 제외
```

초안에서는 worker 안에 렌더러와 해석기를 함께 두고, 기능이 커질 때 분리한다. 패키지 수를 늘리는 것보다 공통 타입과 원본 재렌더 규칙을 지키는 게 우선이다. 로컬 초안은 `/Volumes/OneTouch/video_interference`에서 작업한다. UI 개발 포트는 `4317`, 워커는 `4318`을 사용한다.

## 현재 프로토타입과 후속 편집 제품

**현재 프로토타입의 중심은 파일 열기 → 시점·구간 선택 → 장면 내용·피드백·그림 저장 → 문서와 스틸 묶음 전달이다.** 해석·승인·렌더·새 버전은 선택적인 편집 기능에서 이어지는 후속 제품 흐름이다. 컷·구간 유지·배속·한글 자막·정적 PNG·음소거·도형 합성과 승인·버전·가져오기·취소 API를 검증했다. 현재 테스트 및 PC 영상 측정은 [오버레이검증](오버레이검증.md)에 기록한다. 아래 표는 현재 코드의 구현 범위다. 이 절 밖의 정밀 앵커·상태·스레드 설계는 후속 편집 제품의 기준이다.

| 이미지 | 참고/삽입 역할, 삽입 이미지는 정적 overlay | 참고 스타일을 실행 가능한 속성으로 번역 |
| 자막·그래픽 | SVG→PNG 한글 자막·텍스트·박스, 고정 최대 3줄 템플릿. 레이어 ID로 수정·제거 요청, 종류·구간·겹침 순서·이전 버전 유지 | 실제 수정 화면 검수, 출력 길이 정책·긴 문구 처리·글꼴·스타일 선택 |

이번 초안은 원본을 보존하면서 **30fps CFR 작업용 영상으로 정규화**한다. 컷·배속과 요청 위치는 30fps 정규화 좌표를 기준으로 계산한다. 렌더도 원본 파일에 동일한 30fps 정규화를 적용한 뒤 누적 편집 스냅샷을 실행하므로 이전 버전 MP4를 다시 편집하지 않는다. 정규화에는 재인코딩이 있으며 원본 VFR 프레임과의 엄밀한 PTS 대응, HDR 보존, 색관리까지 보장하지 않는다. 최대 작업 화면은 1920×1080 범위에 맞추므로 원본 4K 품질을 유지한 최종 출력은 후속이다.

초안의 타임스탬프 선택은 브라우저 `currentTime`과 30fps 계산을 사용한다. 요청 카드는 현재 버전을 유지하며 대응 구간과 그림 기준 프레임을 보여 준다. 삭제된 대상은 다른 장면으로 옮기지 않고 작성 버전을 별도로 열 수 있다. 1/30초 이동 버튼과 구간 투영이 있어도 원본 PTS 및 브라우저 표시 프레임의 정밀 확인까지 구현된 것은 아니다. 자동 전사는 연결되지 않았고 녹음 내용을 사용자가 직접 입력해야 한다. API가 없는 자연어 해석은 “로컬 규칙 해석 · AI API 미연결”로 표시한다.

그림마다 작성 프레임을 보존하며, 프레임을 이동해도 이전 그림의 기준이 바뀌지 않는다. 장면 목록에서 그림을 찾아가고 현재 프레임의 그림만 수정·지울 수 있다. 새 요청에 복사할 때는 장면을 선택하며, 컷으로 사라진 그림은 작성 버전에서 확인한다. 여러 장면의 위치 메모를 한꺼번에 정적 그래픽으로 겹쳐 넣지 않는다. 영상에 넣을 때는 한 장면의 그림을 새 요청으로 복사해 구간을 정하고 승인한다. 음성을 첨부한 초안은 녹음 당시의 구간·그림을 고정하며, 변경하려면 음성 첨부를 제거한다.

기본 앱의 자료 준비는 **로컬 처리**다. 이후 사용자가 필요한 AI API 테스트에 Gemini 사용을 지시했으므로, 선택한 피드백·스틸·그림을 읽는 [별도 Gemini 테스트](Gemini테스트.md)를 추가했다. 저장된 장면 설명·피드백 원문·보완 이력·그림 좌표·관련 스틸·참고 이미지·음성을 자료 묶음으로 준비하고, 외부 AI에 전송하지 않는다. 상단 ‘피드백 내보내기’에서 시간별 문서를 복사하거나 MD·JSON·이미지·오디오 ZIP을 받을 수 있다. 영상 파일은 포함하지 않는다. 기존 개별 AI용 자료 준비는 편집 기능 안에 남겨 둔다. 실제 AI 해석과 자동 음성 전사는 후속 연결·검증 범위다. 로컬 규칙 모드는 참고 이미지의 픽셀이나 분위기를 이해하지 않으며, 현재 렌더러는 정해진 텍스트·이미지·박스 파라미터를 사용한다. 참고 이미지의 글꼴·색상·레이아웃을 자동 복제하는 기능으로 표현하지 않는다. 같은 요청 카드에서 원문·앵커를 유지하고 추가 지시를 이력으로 저장한 뒤 명시적으로 재해석할 수 있다. 보완 저장은 이전 승인을 해제한다. 질문·답변 스레드와 승인 대상 revision·계획 해시의 연결은 아직 구현되지 않았으며, 이미 적용한 자막·그래픽은 ‘적용된 자막·그래픽’에서 대상 레이어를 지정하는 새 수정·제거 요청으로 변경한다. 현재 버전은 유지하고 승인한 변경을 다음 버전에서 실행한다. 로컬 자료 묶음에는 대상 레이어와 현재 수정안도 보존한다. 레이어의 종류와 노출 구간 변경은 이번 구현에 포함하지 않는다. 실제 화면 검수와 AI 연결의 남은 범위는 [완료 감사](완료감사.md)를 따른다.

## 개발 순서와 통과 기준

| 단계 | 개발할 것 | 통과 기준 |
|---|---|---|
| 1 리뷰와 저장 | 플레이어, I/O, 드로잉, 요청·메모 | 닫고 다시 열어도 요청과 범위가 복원됨 |
| 2 실행 가능한 초안 | 명령 스키마, 승인, cut·trim·speed, 버전 | 실제 MP4가 생성되고 원본으로 돌아갈 수 있음 |
| 3 AI 해석 | 멀티모달 맥락, 구조화 응답, 질문 | 명확한 요청은 제안되고 불명확한 요청은 보류됨 |
| 4 타이밍과 레이어 | PTS 매핑, 자막, 이미지·제목, 음량 | 컷·배속 후에도 같은 장면과 위치에 적용됨 |
| 5 음성과 검수 | 녹음·전사, 참고 역할, 대응 버전 비교 | 지시 자료가 본편에 잘못 들어가지 않음 |
| 6 일상 사용 | 취소·복구·백업, 성능 측정, 데스크톱 | 자신의 영상에서 반복 수정과 내보내기를 완료 |

기간은 대상 영상과 실제 렌더 시간을 측정한 뒤 정한다. 첫 성공 기준은 “여기 줄여줘”가 승인 가능한 컷 작업으로 보이고, 승인 후 수정 MP4가 나오는 것이다.

### 필수 검증 시나리오

1. 60초 CFR 영상의 12–18초에 2배속을 적용해 57초 결과를 만들고 음성 싱크를 확인한다.
2. 원본 24초에 남긴 요청이 새 버전의 대응 장면 21초를 가리킨다.
3. 메모·드로잉·음성 지시는 승인한 출력 레이어가 없으면 결과에 포함되지 않는다.
4. 승인하지 않은 작업은 실행되지 않는다. 명령 수정 후에는 승인을 다시 받아야 한다.
5. 삭제한 구간의 요청은 삭제 상태로 남고 다른 장면으로 이동하지 않는다.
6. 첫 수정 결과에 두 번째 수정을 적용하고 원본에서 다시 렌더한다. 첫 결과 MP4를 원본으로 쓰지 않는다.
7. 원본에 음성 트랙이 없어도 컷·배속이 완료된다. 빈 범위·전체 삭제·겹친 배속은 렌더 전에 거절한다.
8. 렌더 실패와 취소는 기존 원본·버전을 손상시키지 않는다. 재시작 후 프로젝트를 복원한다.
9. MVP 단계에서 세로·회전·VFR 샘플과 한글 자막·정적 PNG 합성을 추가 검증한다.

정밀 시간축은 계산값으로 검사하고, CFR 출력의 컷 경계는 출력 1프레임 이내를 목표로 확인한다. 음성 싱크는 길이 검사와 별도로 듣고 확인한다. 가져오기·해석·미리보기·최종 렌더 시간은 따로 측정한다.

## 후속 확장

전사 문구 선택 편집, 파형, 자막 템플릿, 로우서드 모션부터 붙인다. 이후 물체 추적과 생성형 B-roll은 별도 작업 엔진으로 연결하고 결과 검수를 유지한다. NLE로 전달하는 OTIO·FCPXML·EDL은 각 포맷에서 컷·배속·자막·그래픽이 어떻게 보존되는지 검증한 뒤 제공한다.

외부 공유와 협업은 현재 개인용 흐름이 안정된 후 추가한다. 그때 원본 업로드, 클라우드 저장, 사용자 권한, 렌더 비용을 별도 설계한다. 첫 제품의 우선순위는 **내 영상에서 위치를 정확히 지정하고, AI의 해석을 승인하고, 실제 수정 결과를 반복 검수하는 것**이다.
