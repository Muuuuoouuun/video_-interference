# 디자인·컴포넌트·속도·사용성 개선 기획

작성 2026-10-22 · 대상: 데스크톱 피드백 프로토타입의 기본 흐름 · 편집 기능(더 보기 → 편집 기능)은 영향 범위만 다룬다.

## 목적

기본 흐름 `영상 확인 → 시점/구간 → 장면·피드백·그림 → 저장 → 피드백 내보내기`를 **피드백이 많아져도 막힘 없이** 쓰게 만든다. 판단 순서는 [제품원칙](제품원칙.md)의 **본질 → 편의성 → 사용성**을 따른다. 시각 정체성(밝은 회색 작업면, 흰 패널, 파란 강조, Pretendard)은 [design-spec](../design/design-spec.md)을 유지하고, 새 디자인을 덧입히기보다 **흩어진 값과 중복 구현을 정리**한다.

이번 기획은 다음 네 가지를 함께 다룬다.

1. **사용성:** 작성창과 구간 지정 같은 주요 행동이 항상 보이고, 지금 보는 것과 작성 중인 것이 구별된다.
2. **속도:** 재생·입력·카드 선택·스크롤이 피드백 150개와 보통 노트북 성능에서도 즉시 반응한다.
3. **디자인 시스템:** 색·글자·간격·모서리를 토큰으로 묶고, 11px 미만 글자를 없앤다.
4. **컴포넌트:** 버튼·팝오버·대화상자·타임코드 같은 기본 부품을 한 곳에서 만들고, 큰 파일을 역할별로 나눈다.

## 지키는 것

- 저장 데이터와 좌표 규칙을 바꾸지 않는다. 댓글 스키마, 30fps 프레임 앵커, 정규화 좌표, `feedback.md`·`manifest.json` 형식은 그대로다.
- 원본과 렌더 스냅샷 보존, 승인한 작업만 렌더하는 규칙을 유지한다.
- 저장·내보내기는 모델을 호출하지 않는다. 로컬 규칙 해석 표시도 유지한다.
- 편집 기능은 계속 ‘더 보기’ 뒤에 둔다. 코드를 분리해도 진행 중인 편집 초안을 잃지 않는다.
- 모바일은 이번 범위에서 제외한다.
- 구조 변경과 시각 변경을 한 커밋에 섞지 않는다. 구조 변경은 화면 결과가 같아야 한다.

## 현재 상태 진단

### 측정 방법과 한계

2026-10-22 클라우드 컨테이너에서 측정했다. 헤드리스 Chromium(Playwright 1.56)으로 실제 앱을 열고, 90초 1080p 합성 영상(`testsrc2`)에 피드백 60개 또는 150개를 로컬 API로 넣었다. 1440×900을 기본으로 하고 1280×800과 1600×1000에서 배치를 확인했다.

- 헤드리스 Chromium은 H.264를 재생하지 못해 **측정용 저장소의 프록시만** VP9/Opus MP4로 바꿨다. 앱 코드와 원본은 바꾸지 않았다.
- 응답 시간은 Event Timing API의 이벤트 지속 시간(16ms 이상만 기록)과 Long Task로 쟀다. 4배 CPU 스로틀은 보통 노트북을 가정한 조건이다.
- 렌더 범위는 개발 빌드에서 React 커밋 훅으로 컴포넌트별 실제 렌더를 셌다. 시간 수치는 프로덕션 빌드 값이다.
- 사용자의 macOS Chrome·실제 영상과는 수치가 다를 수 있다. Phase 0에서 같은 시나리오를 사용자 PC에서 다시 측정한다.

### 응답 시간 (프로덕션 빌드)

| 상황 | 피드백 60개 · 스로틀 없음 | 피드백 150개 · 4배 스로틀 | 원인 |
| --- | --- | --- | --- |
| 첫 화면 (카드·영상 준비) | 469ms | 1,684ms | 원인 미분석 (참고 수치) |
| 재생 5초 | 커밋 22회, 최대 16ms | 최대 48ms, Long Task 1회(59ms) | `timeupdate`마다 App 전체 렌더 |
| 입력 40자 | 최대 32ms | **최대 216ms**, Long Task 150ms | 첫 글자에 목록 카드 전체 렌더 |
| 카드 선택 | 최대 48ms | **최대 256ms**, Long Task 168ms | 선택이 바뀌면 카드 전체 렌더 |
| 목록 스크롤 | 최대 24ms | **최대 104ms**, 느린 이벤트 130개 | DOM 6,235개, 화면 밖 카드도 그대로 배치 |
| 시간축 드래그 40단계 | 최대 32ms | 최대 72ms | 탐색 프레임마다 App 전체 렌더 |

영상 위 그림 드래그도 측정했지만 자동 조작으로 도형이 실제로 만들어졌는지 확인하지 못해 표에서 뺐다. Phase 0 도구에서 도형 생성 확인을 포함해 다시 잰다.

반응이 즉시로 느껴지는 기준은 100ms, 체감 지연은 200ms다. 피드백이 쌓이면 **입력 시작·카드 선택·스크롤이 200ms를 넘는다.** 데이터는 적은데 렌더 범위가 넓은 문제이므로 구조를 고치면 해결된다.

### 렌더 범위 (개발 빌드, 피드백 150개)

- **재생 중:** 3초에 App이 12번 렌더된다. 그때마다 `VideoWorkspace`(현재 프레임과 매번 새로 만드는 콜백 8개), `Composer`, 닫혀 있는 `ShortcutDialog`·`FeedbackTrashDialog`·`FeedbackExportDialog`까지 다시 그린다.
- **첫 글자 입력:** 초안 상태가 바뀌면서 `feedbackHeaderActions`·`selectAuthored`·`previewOverlay`가 새로 만들어지고, `memo`한 `RequestPanel`이 카드 150개를 모두 다시 그린다. 두 번째 글자부터는 `Composer`만 렌더된다.
- **카드 선택:** `selectedId`와 함께 콜백 여러 개가 바뀌어 목록 전체가 다시 그려진다. 카드 단위 `memo`가 없어 바뀐 카드 2개만 그릴 수 없다.

### 화면 배치

- **작성창이 첫 화면에 보이지 않는다.** 작성창은 댓글 목록과 같은 스크롤 영역(`.request-rail`)의 맨 아래에 있다. 피드백 150개에서는 약 31,400px 아래에 있으며 1280×800·1440×900·1600×1000 모두 처음에는 보이지 않는다. ‘작성창을 항상 표시한다’는 [design-spec](../design/design-spec.md)의 기준과 다르다. 지금은 `C`를 누르거나 끝까지 스크롤해야 쓸 수 있다.
- **기본 타임라인 높이에서 주요 버튼이 숨는다.** `.vi-timeline-dock`의 내용은 370px인데 기본 높이는 240px다. ‘구간 지정 I / O’는 절반이 가려지고 ‘구간·시안 펼치기’와 ‘현재 시점에 피드백’은 타임라인 안쪽을 스크롤해야 보인다. 세 화면 크기에서 모두 같다.
- **카드가 크다.** 본문 3줄 카드는 약 180px, 장면 설명·그림이 있는 카드는 289px다. 1440×900에서 한 번에 3–4개만 보인다. 모든 카드가 ‘+ 추가 지시’ 한 줄을 따로 차지하고, 버전이 하나뿐이어도 ‘현재 v1’을 표시한다.
- **저장 카드를 열면 그림 도구 줄이 사라진다.** 같은 자리에 읽기 전용 안내가 나타나 화면이 바뀐다. 보는 중인지 작성 중인지를 배치 변화로만 알 수 있다.
- **마커가 묶음으로만 보인다.** 피드백 62개·90초에서 마커 줄은 `3 +8`, `10 +7` 같은 묶음 8개가 된다. 묶음 안의 위치 분포는 보이지 않는다.
- **글자가 작다.** 1440×900에서 숨김이 아닌 글자 요소 1,196개 중 366개(31%)가 11px 미만이다. CSS 선언은 9px 12개, 10px 101개다. 도구 옆 단축키 글자(V·B·E…)가 대표적이다.

### 디자인과 코드 구조

| 항목 | 현재 | 문제 |
| --- | --- | --- |
| 색상 | CSS 22개 파일에 16진수 색 731개 | 옛 다크·민트 `styles.css`(예: `#bcf7de` 22회)를 `theme.css`가 덮는다. `main.tsx`가 App을 먼저 불러와 컴포넌트 CSS가 두 파일보다 앞에 놓이고, 우선순위가 불러오는 순서에 의존한다. |
| 글자·모서리 | 글자 크기 9–14px 다수, 모서리 3·4·5·6·7·8·10·12px | 기준 표가 있어도 값이 흩어져 있다. |
| 기본 부품 | 공용 부품 없음 | 대화상자·팝오버 14곳(네이티브 `<dialog>` 6, `role="dialog"` 8)을 각자 구현하고, Esc 처리 코드가 12곳에 있다. 도움말은 `title` 속성 80곳으로 따로 단다. 버튼은 전역 `.primary/.secondary/.quiet`와 컴포넌트별 클래스가 섞여 있다. |

| 글꼴 | `PretendardVariable.ttf` 6.4MB | 매번 전체를 받는다. 워커의 정적 응답에 캐시 헤더가 없고 `.ttf`를 `application/octet-stream`으로 보낸다. |

좋은 점도 있다. 시간·구간·그림·투영 계산은 이미 `packages/core`의 순수 모듈 24개로 나뉘어 있고 각각 테스트가 있다. UI 정리는 이 계산을 그대로 쓰면서 화면 쪽만 다시 나누면 된다.

참고로 이 측정의 프록시는 1080p·0.5초 GOP로, 61MB 원본에서 74MB가 됐다. 탐색 반응과 저장 공간에 영향을 줄 수 있으나 내보내기 스틸 품질과 연결되므로 이번 기획에서는 바꾸지 않고 조사 항목으로만 둔다.

## 디자인 시스템

### 토큰

현재 변수 이름(`--canvas`, `--surface`, `--text`, `--accent` 등)은 이미 수백 곳에서 쓰므로 그대로 둔다. 빠진 범주만 더해 `apps/web/src/tokens.css` 하나에 모은다.

| 범주 | 값 | 규칙 |
| --- | --- | --- |
| 색 | 기존 면·글자·강조·위험·주의 + `--playhead`, `--range`, `--recording`, 분류 4색(`--cat-video/subtitle/audio/effect`과 `-soft`, `-ink`) | 컴포넌트 CSS에는 16진수를 쓰지 않는다. 사용자가 그린 선·도형 색은 데이터이므로 토큰이 아니다. |
| 글자 | 11 보조 · 12 메타·타임코드 · 13 입력·버튼 · 14 본문 · 15 섹션 제목 · 17 워드마크 | **11px 미만 금지.** 시간은 `--time-font`와 tabular 숫자를 쓴다. |
| 간격 | 4 · 8 · 12 · 16 · 20 · 24 · 32 | 카드 안쪽 기본 12, 패널 안쪽 16 |
| 모서리 | 6 칩·작은 버튼 · 8 버튼·입력 · 12 카드 · 16 패널·대화상자 | 현재 8가지 값을 4가지로 줄인다. |
| 높이 | 컨트롤 28 · 32 · 38, 클릭 영역 최소 28 | 마커·손잡이처럼 작은 표시도 28px 클릭 영역을 둔다. |
| 그림자·겹침 | 팝오버 1단계, 대화상자 1단계 · z-index: 영상 위 도구 < 팝오버 < 대화상자 < 알림 | 겹침 순서 값을 컴포넌트에서 따로 정하지 않는다. |
| 움직임 | 120ms · 200ms | `prefers-reduced-motion`이면 전환을 끈다. |

### 스타일 정리 순서

1. `tokens.css`를 만들고 `main.tsx`에서 **가장 먼저** 불러온다. 그다음 기본 요소 스타일, 그다음 컴포넌트 CSS 순서로 고정한다.
2. `styles.css`의 옛 다크·민트 값 중 아직 화면에 쓰이는 것을 컴포넌트 CSS로 옮기고, `theme.css`가 덮어쓰던 규칙을 원래 자리에 합친다. 마지막에 두 파일의 덮어쓰기 구조를 없앤다.
3. 컴포넌트 CSS의 16진수 색과 9·10px 글자를 토큰으로 바꾼다. 남은 개수를 테스트에서 세어 늘지 않게 한다.
4. 편집 기능 화면(레이어·이미지 배치·Premiere 대화상자)도 같은 단계에서 캡처를 비교한다. 자주 열지 않는 화면이라 회귀를 놓치기 쉽다.

## 컴포넌트 계획

### 기본 부품 (`apps/web/src/ui/`)

외부 UI 라이브러리를 더하지 않고 작은 부품을 직접 만든다. 지금 의존성이 적고, 필요한 동작(포커스 복귀·Esc·한글 조합 중 단축키 무시)이 앱 고유 규칙과 묶여 있기 때문이다.

| 부품 | 대체하는 것 | 규칙 |
| --- | --- | --- |
| `Button` | `.primary/.secondary/.quiet`, 컴포넌트별 버튼 | 종류: 주요·보조·조용함·위험, 크기 28/32 |
| `IconButton` | `title`과 `aria-label`을 따로 다는 아이콘 버튼 | 이름 필수, 도움말에 단축키 표시, 최소 28px |
| `Popover` | 그림 스타일, 겹친 마커 목록, 더 보기, 도구 팝업 | 기준 요소에 붙고, Esc·바깥 클릭으로 닫으며 연 버튼으로 포커스를 돌린다. |
| `Dialog` | 내보내기·Premiere·레이어·휴지통·단축키·이미지 확대 | 네이티브 `<dialog>` 기반, 열 때만 마운트, 닫으면 포커스 복귀 |
| `Timecode` | 플레이어·마커·카드·작성창의 시간 표기 | 소수 둘째 자리, 시점은 시계, 구간은 대괄호 아이콘 |
| `Badge` / `Chip` | 번호 배지, 분류, 개수 | 22px 번호 배지, 분류 색은 토큰 |

공용 Esc·바깥 클릭·포커스 복귀 처리는 `useDismiss`와 `useFocusReturn` 훅 하나로 모은다. 기존 [키 규칙](피드백프로토타입.md)(입력·한글 조합 중 단축키 무시, 그림 영역의 Delete 구분)을 이 훅에서 지킨다.

## 단계별 일정

규모는 S(하루 이내), M(2–3일), L(4일 이상)로 적는다. 각 단계는 끝날 때 `npm run build`, `npm test`, Phase 0 측정을 통과하고 수치를 이 문서에 기록한다.

### Phase 0 · 기준선 고정 (S)

- `scripts/measure-ui.mjs`: 이번 진단의 시나리오(첫 화면, 재생, 입력, 카드 선택, 스크롤, 시간축 드래그, 박스 드래그)와 배치 검사(작성창 보임, 타임라인 버튼 가려짐, 11px 미만 글자)를 실행한다. `playwright-core`를 개발 의존성으로 두고, 로컬 Mac에서는 설치된 Chrome(`channel: 'chrome'`)을, 클라우드에서는 미리 설치된 Chromium과 VP9 측정용 프록시를 쓴다. 피드백 60·150개 시드를 포함한다.
- 결과는 `storage/qa/ui-metrics/`에 JSON과 화면 캡처로 남긴다(Git 제외).
- 테스트 이식성: `tests/engine-api.test.mjs`의 `/opt/homebrew/bin/ffprobe` 고정 경로를 엔진의 `ffprobePath`로 바꾼다. 이번 Linux 측정에서는 `FFMPEG_PATH`·`FFPROBE_PATH`를 지정해도 이 검사가 실패했고, FFmpeg 6.1.1에서 투명 배치 픽셀 검사 1개가 추가로 실패했다(289/291 통과). 픽셀 검사 실패의 원인은 확인하지 않았으며 macOS FFmpeg에서 다시 확인한다.

### Phase 1 · 핵심 흐름의 막힘 해소 (M)

U1 작성창 고정, U2 타임라인 주요 행동 정리, U5 머리 축소, S1–S3 렌더 범위 격리. 사용자가 바로 느끼는 문제와 위험이 낮은 속도 개선을 먼저 묶는다.

완료 기준: 작성창·타임라인 지표 통과, 카드 선택 100ms 이하, 첫 입력 50ms 이하.

### Phase 2 · 토큰과 기본 부품 (M)

`tokens.css`, CSS 불러오기 순서 고정, `styles.css`·`theme.css` 덮어쓰기 정리, `Button`·`IconButton`·`Popover`·`Dialog`·`Timecode`·`Badge`·`Disclosure`. U7 글자 하한, U9 팝업 통일, S7 글꼴.

완료 기준: 11px 미만 0%, 토큰 밖 16진수 색 0개, 팝업 키보드 검사 통과, 기본·편집 화면 캡처 비교에서 의도하지 않은 차이 없음.

### Phase 3 · 구조 분리와 재생 시각 저장소 (L)

App 훅 분리, `RequestPanel`·`VideoWorkspace`·`Composer` 분리, S5 재생 시각 저장소, S4 목록 화면 밖 렌더 생략, S6 편집 기능 지연 로드.

완료 기준: 재생·드래그 중 App 렌더 0회, 스크롤 50ms 이하, 기존 계산·SSR·native 테스트 전부 통과, 프레임 정확도 관련 화면 검수(C 키 시점, 초안 복귀, 구간 반복) 통과.

### Phase 4 · 정보 밀도와 상태 표시 (M)

U3 보는 중 표시, U4 카드 밀도, U6 마커 분포, U8 저장·내보내기 결과 표시. 디자인 결정이 필요한 단계라 Phase 3 뒤 화면 캡처를 사용자에게 먼저 보여 주고 진행한다.

완료 기준: 카드 6개 이상 보임, 카드 선택 전후 도구 줄 위치 동일, 사용자 PC에서 기본 흐름 한 바퀴(영상 열기 → 피드백 10개 → 내보내기) 검수.

## 검증

- **자동:** 기존 `npm test`(계산·SSR·native) 유지. 기본 부품은 기존처럼 `react-dom/server` 출력으로 이름·상태 속성을 검사한다. CSS의 16진수 색·11px 미만 글자 수를 세는 검사를 더한다.
- **실제 브라우저:** Phase 0 측정 도구로 수치와 캡처를 남긴다. 계산 검사나 SSR 검사로 화면 조작 검수를 대신하지 않는다는 기존 원칙을 유지한다.
- **사용자 PC:** 각 Phase 끝에 macOS Chrome과 실제 영상으로 같은 측정을 한 번 한다. 클라우드 측정과 다르면 사용자 PC 값을 기준으로 한다.
- **기록:** 결과와 남은 조건은 [완료감사](완료감사.md)와 [오버레이검증](오버레이검증.md)의 기존 형식으로 남긴다.

## 결정이 필요한 것

1. **작성창 위치:** 댓글 패널 아래 고정(권장), 패널 위 고정, 영상 위 떠 있는 입력 중 무엇으로 할지. 권장안은 목록을 보며 쓰는 현재 흐름과 C 키 동작을 그대로 유지한다.
2. **카드 밀도:** 촘촘한 카드 하나로 갈지(권장), ‘넓게/촘촘하게’ 전환을 둘지. 전환은 설정 상태를 하나 더 만든다.
3. **탐색용 프록시 조사(S8):** 긴 영상에서 탐색 반응을 재는 조사를 이번에 할지. 결과에 따라 프록시 해상도 변경을 별도로 결정한다.
